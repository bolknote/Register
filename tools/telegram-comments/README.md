# Импорт комментариев через Telegram Serverless

Этот бот переносит новые комментарии из привязанной к каналу группы обсуждения в Register.
Он обрабатывает сообщения, правки, посты канала и изменения реакций, сохраняет события
в SQLite у Telegram и передаёт их в `POST /_live/telegram/comments` на сайте. Отдельный сервер для
бота не нужен. Публикация статей в канал в эту версию не входит.

В исходном посте канала должна быть **одна ссылка на статью блога в первой строке** — обычная
ссылка либо ссылка в заголовке. Статья должна быть опубликована. Исторические адреса статей
поддерживаются через существующие URL aliases Register. Произвольные сообщения группы и
пересылки постов вручную не связываются со статьями.

## Создание и подключение

1. Создайте отдельного бота в [@BotFather](https://t.me/BotFather) командой `/newbot`.
   Откройте [мини-приложение BotFather](https://t.me/BotFather?startapp), выберите бота →
   **Serverless** → включите Serverless. Обычные текстовые меню `/mybots`, **Edit Bot** и
   **Bot Settings** могут не показывать этот раздел. Если пункта нет и в мини-приложении,
   ранний доступ ещё не доступен этому боту. Сохраните Bot API token для связи с настройками блога.
2. На компьютере с Node.js 18+ перейдите в каталог этого проекта:

   ```sh
   cd tools/telegram-comments
   npm ci --ignore-scripts
   npx tgcloud init --no-git
   cp config.example.js tgcloud/lib/config.js
   chmod 600 tgcloud/lib/config.js
   npx tgcloud login
   ```

   `login` запросит отдельный **CLI Access token** из BotFather → Serverless → CLI Access.
   Введите его непосредственно в терминале. Файл конфигурации и `.tgcloud/` исключены из Git.
   `init` сохраняет имеющийся код и создаёт служебное состояние проекта; `--no-git` отключает
   создание вложенного Git-репозитория и коммита.
3. Выполните `npx tgcloud push`, затем `npx tgcloud migrate --safe`. Напишите боту `/start`
   в личном чате: он сообщит ваш Telegram ID. Впишите его в `ownerUserId` файла
   `tgcloud/lib/config.js` и повторите `npx tgcloud push`.
4. Добавьте бота **администратором и в канал, и в группу обсуждения**. Telegram передаёт
   изменения реакций только администраторам. Права публикации и удаления сообщений
   для импорта не требуются.
   От своего аккаунта отправьте `/ids@имя_бота` в группе. Бот вернёт `chat_id` группы и
   `linked_chat_id` канала. Сохраните их в `discussionChatId` и `channelChatId`. Если
   `linked_chat_id` отсутствует, сначала привяжите эту группу к каналу в настройках Telegram.
5. Сгенерируйте **отдельный секрет связи с блогом**:

   ```sh
   php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
   ```

   Укажите его в `token`, а канонический HTTPS-адрес блога — в `blogUrl`. Этот секрет не
   является ни Bot API token, ни CLI Access token. Не отправляйте токены в чаты.
6. В панели Register откройте **Настройки → Telegram**. Укажите оба числовых ID, свой ID
   из `/start`, выберите учётную запись автора блога и включите импорт. Сохраните ключ
   импорта из `token` и токен Bot API. Последний также укажите в `botApiToken` приватного
   `tgcloud/lib/config.js`. Значения ключей не показываются в форме и вынесены из базы
   и кеша настроек в приватное хранилище Register.

   Бот получает эти настройки по HTTPS через защищённый `GET /_live/telegram/config`
   перед доставкой, сохраняет их в своей SQLite и использует при следующих событиях.
   Недоступность сайта не удаляет очередь или последние настройки. После смены токена
   Bot API в BotFather замените его и в настройках блога, и в `botApiToken` бота и загрузите код;
   изменение ID и ключа импорта повторной загрузки кода не требует.
   Старая секция `telegram_import` из `config.php` автоматически переносится при обновлении;
   после этого сохранённые настройки имеют приоритет, включая выключение импорта.
   Внутренние ID Telegram Desktop и Bot API различаются; настройки принимают отрицательные
   **Bot API ID** из `/ids`. Без корректного ключа и обоих ID вход отключён.
7. Выполните `npx tgcloud push`, затем `npx tgcloud webhook sync` без `--drop-pending`.
   `npx tgcloud webhook` должен показывать `message`, `edited_message`, `channel_post`,
   `edited_channel_post`, `message_reaction`, `message_reaction_count` и
   состояние **In sync**. Не настраивайте для этого же бота второй webhook или `getUpdates`.
8. Оставьте комментарий с картинкой или стикером под постом канала со ссылкой в первой строке.
   Проверьте его в блоге и в панели управления, затем ответ, правку подписи, добавление и снятие
   реакции. Для проверки реакций самого поста используйте новый или отредактированный после
   подключения бота пост канала. При включённой премодерации
   комментарии сначала попадают на проверку. В личке бота команда `/status` показывает
   очередь; `/retry` повторяет до 20 ожидающих событий.

## Поведение и ограничения

- Сохраняются имя отправителя, время сообщения и цепочка ответов. Сообщения от имени
  связанного канала или группы распознаются как сообщения автора сайта, как при архивном
  импорте. «Твой ID в Telegram» также связывает личные сообщения владельца с существующим
  профилем автора блога: его именем и аватаром. Остальные Telegram-пользователи не получают
  локальную учётную запись или выдуманный email. Основные стили и ссылки, включая Rich Messages,
  переводятся в существующий безопасный формат комментариев Register. При перекрывающихся
  стилях приоритет имеет ссылка; весь видимый текст сохраняется.
- Используются те же идентификаторы импорта, что при загрузке Telegram Desktop export.
  Повторная отправка и старые архивные комментарии не создают дубликатов. Ручные исправления,
  скрытие и удаление в блоге не отменяются правкой из Telegram. Обычная правка комментария
  не изменяет реакции: они обновляются отдельными событиями.
- Лайки и остальные реакции постов и комментариев импортируются, включая снятие реакции.
  Повторная доставка и перестановка личных реакций не удваивают счётчики. Анонимные реакции
  канала приходят абсолютными счётчиками, иногда с задержкой в несколько минут. Локальные
  реакции посетителей блога сохраняются. Нестандартные Telegram emoji сохраняют свой ID и
  количество и показываются как «✦»; платные реакции показываются как «⭐».
- Картинки, видео, GIF/анимации, аудио, голосовые сообщения, видеокружки, документы и стикеры
  сохраняются в управляемое хранилище блога. Бот передаёт только непрозрачные `file_id`, а сайт
  скачивает файлы через свой сохранённый Bot API token. Токен и временные Telegram URL не
  попадают в публичный HTML. Уже сохранённые файлы не скачиваются снова при правке подписи.
  WebP-стикеры отображаются картинками, WebM — зацикленным видео, TGS — локальным Lottie
  canvas-плеером без вычисления выражений и загрузки внешних ресурсов. Плеер загружается
  только при появлении стикера на экране; учитываются невидимая вкладка и reduced motion.
- Telegram Bot API позволяет скачивать файлы до **20 МБ**. Более крупные вложения остаются
  пометками недоступного файла; их можно дополнить полным ZIP-экспортом Telegram Desktop.
  Ошибка сети при скачивании не подтверждает событие: оно остаётся в очереди для повтора.
- Перед HTTP-запросом событие сохраняется в базе бота. При ошибке оно остаётся в очереди.
  Повторная доставка запускается **следующим сообщением в группе или командой владельца
  `/retry`**. Автономного таймера здесь нет: восстановление сайта само по себе бота не запускает.
  Отсутствие успешного подтверждения от сайта также сохраняет событие для повторной доставки.
- Новые ответы на старый пост импортируются, если Telegram включает автоматически
  пересланный корневой пост в `reply_to_message`. Для вложенного ответа нужен известный боту
  родитель и его связь с корнем. Если эта часть истории появилась до подключения бота,
  ответ остаётся в очереди с `missing_parent`; повтор без появления недостающей истории
  сам по себе её не восстановит. Bot API не предоставляет произвольную историю сообщений.
  Историю можно отдельно загрузить через существующий архивный импорт Register; загрузка
  архива на сайте не заполняет базу этого бота. Реакция на старый комментарий может найти его
  архивную идентичность на сайте. Реакция на неизвестный пост канала остаётся с `missing_target`,
  пока бот не увидит сам пост или его автоматическую пересылку с исходным channel message ID.
  Bot API не выдаёт начальные счётчики личных реакций или историю старых постов; для полного
  исходного состояния используйте архивный импорт. Последующие события обновляют его.
- Удаления сообщений Telegram не синхронизируются. Максимальная цепочка — 64 комментария,
  запрос метаданных — 256 KiB; бинарные файлы в запросе не передаются.
- База сообщений сохраняется для будущих ответов; автоматической очистки истории нет.
  Это отдельный бот для одной пары «канал + группа». При смене группы кеш предков очищается,
  а события прежней группы остаются в очереди с `scope_changed` и не отправляются в новый контекст.

В `/status` ошибки `http_401_*` означают несовпадение секрета, `http_404_*` — отсутствие
входа или отключённую конфигурацию, `http_409_post_not_found` — ещё не опубликованную статью
или неизвестный адрес, `http_422_invalid_snapshot` — неверную ссылку или цепочку.
`http_409_missing_target` — неизвестный пост или комментарий; `http_503_media_download_failed`
— временная ошибка скачивания вложения. `network_error` и `http_503_busy` сохраняют события
до следующего повтора. Секреты и тексты
комментариев в диагностические ответы не выводятся.

## Если прямое соединение недоступно

Некоторые хостинги не могут подключиться к Telegram API, а Telegram Serverless — к самому
блогу. В этом случае можно использовать собственный узкий HTTPS-шлюз с проверкой сертификатов
обоих upstream. В настройках Telegram есть необязательные **Адрес HTTPS-шлюза** и
**Ключ HTTPS-шлюза**. Ключ отдельный, случайный, из 64 шестнадцатеричных символов; он хранится
приватно, как остальные ключи.

Шлюз проверяет `X-Register-Telegram-Relay-Key`, затем перенаправляет `/blog/_live/telegram/config`
и `/blog/_live/telegram/comments` в блог, `/api/bot<TOKEN>/getFile` и `/api/file/bot<TOKEN>/…` —
в Telegram API. Разрешайте только собственный токен бота и эти маршруты; выключите журналирование
URI с токенами. Доступ без ключа должен возвращать 401, остальные пути — 404. Изменения служб
шлюза и его TLS настраиваются владельцем отдельно от развёртывания Register.

Также укажите `relayUrl` и `relayToken` в приватном `tgcloud/lib/config.js`, затем загрузите
бота: это первоначальный маршрут для получения настроек. Канонический `blogUrl` остаётся адресом
самого блога и используется для сопоставления ссылок на статьи. Бот получает последующие изменения
шлюза через защищённый конфигурационный endpoint. При смене relay key синхронно обновите его
в шлюзе, в настройках блога и в приватной конфигурации бота.

## Проверки без Telegram

Из корня Register:

```sh
node --test _tests/javascript/telegram-comments.test.mjs
APP_DB_TYPE=sqlite _vendor/bin/codecept run --config=_tests/codeception.yml integration --filter Telegram --no-interaction
```

JavaScript-проверки используют настоящую SQLite и общий с PHP снимок обсуждения. Они
покрывают повторную доставку, ошибки сети, ответы раньше родителей, порядок правок и
фильтрацию групп. Интеграционные проверки проходят через HTTP-маршрут Register и проверяют
авторизацию, дерево комментариев, премодерацию и совместимость архивного и живого импорта.

Документация платформы: [Telegram Serverless](https://core.telegram.org/bots/serverless),
[Bot API](https://core.telegram.org/bots/api),
[получение сообщений ботами](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).
